# Frontend Architecture

Implements the PRDs in `kb/platform/frontend.md` and `kb/platform/app-shell.md`. Code lives in `frontend/`. Setup commands are in `frontend/README.md`.

## Overview

A single Angular 22 application using standalone components (no NgModules), strict TypeScript and strict templates, zoneless change detection, and Spartan UI (on Tailwind CSS v4) as the UI library. It is organized by feature. It contains shared infrastructure only (API access, errors, notifications, theme, shell); there is no business feature yet. The first business feature, specified in its own PRD, will follow the conventions below.

Every page is displayed inside an application shell (header, sidebar menu, content area), and the Dashboard is the landing page.

Not implemented on purpose: authentication, user menu, route guards, breadcrumbs, nested menu groups.

## Project and folder structure

The Angular project sits directly in `frontend/` (`package.json`, `angular.json`, `src/` are direct children).

```
frontend/
  components.json            Spartan CLI config (where helm components are generated)
  .postcssrc.json            Tailwind CSS v4 PostCSS plugin
  proxy.conf.json            dev-server proxy: /api -> backend
  src/
    styles.css               Tailwind import and Spartan theme (CSS variables)
    environments/            environment.ts, environment.development.ts (apiBaseUrl)
    app/
      app.ts                 root component: router outlet and the toaster
      app.config.ts          providers: router, HttpClient + interceptors
      app.routes.ts          lazy routes
      core/
        api/                 API_BASE_URL token, apiBaseUrlInterceptor
        errors/              ApiError, toApiError, httpErrorInterceptor
        navigation/          NAV_ITEMS, NAV_ICONS and the NAV_MENU token: the single list behind the menu and Dashboard quick links
        notifications/       NotificationService
        theme/               ThemeService (light/dark)
      shell/                 Shell (header with theme switch, sidebar, sheet, content outlet) and AppNav (the menu)
      shared/
        ui/                  Spartan helm components generated by the CLI (only the ones in use)
      features/
        dashboard/           Dashboard landing page
        <area>/<feature>/    business features are added here (none yet)
```

## Boundary rules

- `features/*` may import from `core` and `shared`.
- `core` and `shared` never import from `features`.
- A feature never imports from another feature. There are no exceptions.
- Only a feature's service talks to the backend. Components and templates never contain URLs.

## Routing

`app.routes.ts` has one parent route whose component is `Shell`. Its children are the Dashboard at `''` and, as features are added, their lazy `loadChildren` routes; any unknown path redirects to `''`. There are no guards. Shell and menu are part of the initial download; the Dashboard and every feature are separate lazy chunks.

## Application shell

`Shell` (`app/shell`) is the frame around every page: a header (app name `iErp`, a menu button for small screens, and the theme switch), a sidebar, and `<main class="page">` with the router outlet. It supplies the page width and padding, so feature pages render only their own content and do not add `<main>`. The toaster stays in `App`, outside the shell. There is no user menu or breadcrumb.

### Menu

`core/navigation/nav-items.ts` exports `NAV_ITEMS`, a typed list of `{ label, icon, route }` (currently only Dashboard `/`), and `NAV_ICONS`, the Lucide icons those items name. Components read the list through the `NAV_MENU` injection token, which defaults to `NAV_ITEMS` and can be overridden in tests. `AppNav` renders the list as a `<nav aria-label="Main menu">` of router links and registers the icons with `provideIcons(NAV_ICONS)`. The current entry gets the `active` class through `routerLinkActive`; Dashboard (`/`) matches exactly, other entries also match pages beneath them (so a page at `/reports/new` highlights an entry for `/reports`). `AppNav` emits `navigated` when an entry is chosen.

### Responsive behavior

At 768px and wider (Tailwind `md`) the sidebar sits beside the content and the header menu button is hidden (`hidden md:block`, `md:hidden`). Below 768px the sidebar is hidden and the button opens the same `AppNav` inside a Spartan `hlm-sheet` (left side). The breakpoint is pure CSS. The sheet's state is a `menuOpen` signal in `Shell`, bound to the sheet's `state` input and `stateChanged` output: the button opens it; choosing an entry (`navigated`) or dismissing the sheet (close button, Escape, overlay click) closes it.

### Theme (light and dark)

`core/theme/theme.service.ts` holds the theme as a signal (`'light' | 'dark'`) with `toggle()` and `set()`. The initial theme is the stored choice (`localStorage`, key `ierp-theme`), else the operating system's `prefers-color-scheme`, else light. The service applies the theme by toggling the `dark` class and the `color-scheme` style on `<html>`. Spartan's generated `:root.dark` variables in `styles.css` and Tailwind's `dark:` variant (`@custom-variant dark` in Spartan's preset) both key on that class, so every component follows it with no per-component code.

To avoid a flash of the wrong theme, a short inline script in `index.html` applies the same stored-else-system rule to `<html>` before the app starts. Keep the script and the service in sync. (A strict Content-Security-Policy would need to allow this script.) Storage access is wrapped in try/catch: if the browser blocks it, the switch still works for the visit but is not remembered.

The header button (`Shell`) shows the theme the user will switch to (moon in light mode, sun in dark mode) and its `aria-label` states the action ("Switch to dark theme" / "Switch to light theme"). Portal-rendered pieces (sheet, alert dialog) inherit the class from `<html>`. The Sonner toaster has its own theme input, so `App` binds it to the service: `<hlm-toaster [theme]="themeService.theme()" />`. In dark mode the text tokens (`--foreground`, card, popover, secondary, accent and sidebar foregrounds) are softened to `oklch(0.87 0 0)` instead of Spartan's near-white `0.985`: about 13:1 contrast on the page background (19:1 before), 12:1 on cards and 10:1 on secondary/accent surfaces, all above WCAG AA. Muted text stays at `0.708`, so it is still dimmer. To change the brightness, edit those values in the `:root.dark` block of `styles.css`. There is no "follow the system" option and no server-side preference.

### Adding a menu entry for a new module

1. Add the module's lazy route as a child in `app.routes.ts`.
2. Add one item to `NAV_ITEMS` (and its icon to `NAV_ICONS`).

The menu and the Dashboard quick links pick it up. The shell does not change.

## Dashboard

`features/dashboard` is the landing page. It shows a heading and a short welcome text, and a "Quick links" section built from the menu list (every entry except the Dashboard itself). While the menu has only the Dashboard, the quick-links section is not shown. The Dashboard shows no data and makes no backend requests, and it imports nothing from other features.

## Spartan UI and Tailwind

Spartan has two layers. `@spartan-ng/brain` is an npm package of unstyled, accessible primitives. `helm` is a set of Tailwind-styled components that the Spartan CLI generates as source into this project, which then owns them. There is no license key.

- Tailwind CSS v4 runs through `@tailwindcss/postcss` (`.postcssrc.json`). `src/styles.css` imports Tailwind and holds the theme (the neutral theme from `ng g @spartan-ng/cli:init`) as CSS variables.
- `components.json` sets the helm output folder to `src/app/shared/ui`. Components are imported through the `@spartan-ng/helm/<name>` path aliases in `tsconfig.json`.
- Generated so far, because the shell uses them: `button`, `sheet`, `sonner` (plus `utils`). Add another with `npx ng g @spartan-ng/cli:ui <name>`; generate only what is used, and remove one that stops being used.
- Font: Roboto, self-hosted with `@fontsource/roboto` (weights 400, 500 and 700 imported in `styles.css`, so the font files are bundled with the app and nothing is requested from an external host). `--font-sans` in `styles.css` lists Roboto first with `sans-serif` and the emoji fonts as fallback; Tailwind and the Spartan components inherit it, and form controls inherit it through Tailwind's preflight. Change the font in that one variable.
- Icons are Lucide through `ng-icon` (`@ng-icons/lucide`); each component registers the icons it uses with `provideIcons`.
- Components are used directly, with Tailwind utility classes for layout. No wrappers. Spartan has no provider setup in `app.config.ts`.

## API integration

- `API_BASE_URL` (from `environment.apiBaseUrl`, default `/api`) is the single source of the backend address.
- `apiBaseUrlInterceptor` prefixes relative URLs with it, so services call `http.get('customers')`. Absolute URLs pass through untouched.
- In development the dev server proxies `/api` to the backend (`proxy.conf.json`), so there are no CORS problems. The backend has no CORS configuration; a deployment on a different origin needs it added.

## Interceptors

Two small functional interceptors, registered in this order in `app.config.ts`: `apiBaseUrlInterceptor`, then `httpErrorInterceptor`. They contain no feature logic and no authentication. Add new cross-cutting concerns as separate small interceptors.

## Notifications and error handling

- `NotificationService` (`success`, `info`, `warn`, `error`) wraps Spartan's Sonner `toast`. The single `hlm-toaster` in `app.ts` renders them. Toasts last 5 seconds and can be closed.
- `httpErrorInterceptor` converts every failed request to an `ApiError { status, message, fieldErrors? }` via `toApiError`, shows one error notification, and rethrows the `ApiError`.
- Messages are fixed, user-friendly texts: network failure (status 0), not found (404), generic (5xx and unknown). Backend exception text is never displayed.
- A 400 with an `errors` map is not notified. `fieldErrors` (keys converted to lower-camel, e.g. `Title` becomes `title`) go to the caller, which shows them next to the fields.
- Features do not notify about failures themselves; they only notify about success.

## Conventions for the next feature (guidance, not yet implemented)

No business feature exists yet, so nothing in the code demonstrates the conventions below. They are the plan for the first feature PRD, which proves or revises them.

- **State.** Feature services own state with signals, close to the feature, provided by the feature's routes (not `providedIn: 'root'`), with `load`, `save` and `remove` and readonly `items`, `loading` and `error` signals. No NgRx.
- **Forms.** Typed Reactive Forms (`FormBuilder.nonNullable`) built from the Spartan input, textarea, checkbox and label. A message shows under a field once it is touched; an invalid form marks every field touched and sends nothing; backend `fieldErrors` (already provided by the error interceptor) are set on the matching controls, and an error for an unknown field goes to a notification; Save is disabled while the request is in flight.
- **Data tables.** The Spartan table components are styling only, so searching, sorting and paging are plain signal code (client-side while the backend returns the full list), with a loading indicator and an empty-state row. Delete asks for confirmation in a Spartan alert dialog before sending the request, then shows a success notification.
- **Generating components.** Generate the Spartan components a feature needs (`table`, `alert-dialog`, `input`, ...) with the CLI when that feature is built.

## Shared UI components

`shared/ui` holds the generated Spartan helm components. Other shared components are added only when a second feature genuinely needs one; keep them free of feature logic and prefer Spartan components directly.

## Testing

Angular's default runner (Vitest) via `npm test -- --no-watch`. No backend or browser needed.

- `toApiError` and the interceptors (`HttpTestingController`).
- `ThemeService`: default light, system preference, stored choice over system, invalid stored value, toggle and class, remembering across visits, blocked storage.
- `NAV_ITEMS`, `AppNav` (entries, links, active highlighting, exact Dashboard match, `navigated`) and `Shell` (header, menu, routed page, sheet opens and closes, theme button name and toggling) tests.
- `Dashboard` component: heading and welcome text, no quick-links section by default, links for extra menu entries (via the `NAV_MENU` token), no backend requests.

## Adding a feature

1. Add its entry to `NAV_ITEMS` and a lazy child route under the shell in `app.routes.ts`.
2. Create `features/<area>/<feature>/` with `<feature>.model.ts`, `<feature>.service.ts`, `<feature>.routes.ts`, and its pages.
3. Make the service own signal state and the backend calls with paths relative to the API base (for example `http.get('customers')`). Provide it in the feature routes.
4. Follow the conventions above: a typed Reactive Form, the Spartan table, `NotificationService` for success, and let the interceptor report failures. Generate any Spartan component you need with the CLI.
5. Pages render only their content (the shell supplies the page frame).
6. Add service and component tests (the interceptor and component tests in this project show the pattern).
7. Update this document if the feature changes a convention.
